# DocBridge · 文档翻译网站（PDF / Word）

把英文（或任意语言）文档翻译成中文的**网站**：浏览器上传 → 排队翻译 → 在线预览 → 下载。
两种输出形式，页面上随时切换：

| 输出形式 | 效果 | 适合 |
|---|---|---|
| **原位版式保留** | 译文覆盖原文，文字/图片位置完全不动 | 教材、论文、报告通读 |
| **双语对照** | 原文与译文并排（PDF）或上下相邻（Word） | 精读、校对、学英语 |

它和同目录的 `同域项目/`（同类项目 实时同声传译）是**同一个站点的两个页面**：
挂同一域名，但**两条线各管各的模型配置**：

| | 配置文件 | 用途 |
|---|---|---|
| 文档翻译（本站） | `docbridge/profiles.json` | 上传 PDF / Word 的批量翻译 |
| 同声传译（同类项目） | `同域项目/profiles.json` | 麦克风实时语音翻译 |

两边互不影响：本站换模型（比如换到 DeepSeek-V4-Flash）不会动到语音站的任何配置。
代价是密钥在两份文件里各有一份，**换密钥要改两处**。

   浏览器（public/，原生 JS，零依赖）
        │  ① 上传文件（相对 URL，路径挂载 /doc/ 或独立子域都能用）
        ▼
   Flask 服务（app.py，:8788）──► 任务队列 jobs.py（每任务独立目录 + SSE 进度）
        │  ② 按「格式 × 模式」选管线
        ▼
   pipelines/ 四条管线，统一 run() 契约（见 CONTRACT.md）
        ├── pdf_inplace    PDF 原位：包装既有 pdf_translate.py（图文不动、段落字号、禁则、缓存）
        ├── pdf_bilingual  PDF 双语：原文页矢量嵌入左半边，译文排在右半边
        ├── docx_pipeline  Word 原位：整段译文写回首个 run，保留段落样式
        └── docx_pipeline  Word 双语：译文段落紧邻插在原文段之后
        │  ③ 管线只通过一个回调拿译文，不关心供应商
        ▼
   translator.py ──► profiles.json 里的预设代号（密钥只留服务端）
                    批量 JSON 翻译 + 五类校验 + 重试 + 逐条兜底

## 快速开始（本机）

```bash
cd docbridge
pip install -r requirements.txt        # 也可以先用系统已装的 flask/pymupdf/python-docx
python3 app.py                         # 打开 http://127.0.0.1:8788
```

> **Linux 上先装中文字体**：`apt install fonts-arphic-uming fonts-wqy-zenhei`。
> 要挑 **TrueType 轮廓**的字体——不装的话 PyMuPDF 会退回内置 `china-s`，
> 字形画得出来但 PDF 里缺 ToUnicode，**译文复制/搜索出来是乱码**；
> 而用 Noto CJK（CFF 轮廓）则字体子集化会失败，输出被撑到十几 MB。
> 用 `python3 tools/check_pdf_font.py` 可一键自查。

密钥来源（按优先级）：页面手填 → `profiles.json` 预设代号 → 环境变量。
部署到服务器、和 同类项目 并存的做法见 **[deploy/DEPLOY.md](deploy/DEPLOY.md)**。

## 翻译通道怎么配（profiles.json）

代号写在服务端 **`docbridge/profiles.json`**（本站自己的文件，与语音站分开），浏览器只拿得到代号：

```json
"relay": {
  "name": "GPT 中转站 · 文档翻译",
  "baseUrl": "https://你的中转站/v1",
  "apiKey": "sk-真实密钥",
  "chatModel": "gpt-5.5",
  "api": "responses"          // 关键：见下
}
```

* **`api` 字段**：`chat`（默认，走 `/chat/completions`）或 `responses`（走 `/responses`）。
  很多 GPT 中转站**只支持 Responses 接口**，对 `/chat/completions` 直接回 405 ——
  同类项目 里也有同一层兼容，这不是 DocBridge 特有的怪癖。
* **密钥必须是真实值且不含中文**：HTTP 请求头只能编码 latin-1，密钥里混入中文
  （典型是没替换的占位符 `sk-你的OpenAI密钥`）会抛出
  `'latin-1' codec can't encode characters in position 10-11` 这种看不懂的错。
  DocBridge 现在会在**提交任务时**就拦下来，并说清是哪个代号、哪个字段有问题；
  不可用的代号会在页面下拉里标 ⚠ 且不可选。
* **被 Cloudflare 拦了（`error code: 1010`）**：有些中转站按 User-Agent 拦截，
  Python 默认的 `Python-urllib/3.x` 会被拒。用环境变量换个 UA 即可：
  `DOCBRIDGE_UA="Mozilla/5.0 ... Chrome/131.0.0.0 Safari/537.36"`。

## 怎么做到更便宜 / 更快 / 更准

PDF 原位模式默认开启**批量预翻译**（`prefetch`，页面上可关）：

1. **跨页攒批**：上游是「一页一次请求」，每页都要重发一遍系统提示与翻译规则。
   预翻译把整份文档的行按 ~50 行/3000 字符攒批，请求数从「页数」降到「行数/50」。
2. **批次并发**（`DOCBRIDGE_PREFETCH_WORKERS`，默认 3）：上游逐页调用是串行的，预翻译的批次可以并行。
3. **认缓存**：预翻译先读上游的页缓存，已翻过的行不重复翻——重复提交或断点续跑时**零请求**。
   缓存键 = 文件内容哈希 + 模型 + 语言对 + **术语表与提示词版本**。最后一项很关键：
   没有它，你改了术语表再重跑会命中旧译文，术语表静默失效（任务显示成功、内容却是旧的）。
4. **文档背景 + 共享术语表**：每批提示里带上文档标题/开头几行，以及
   `同域项目的 glossary.json`（两个站点共用同一份术语表）中**本批真的出现**的词条。
   没有上下文时模型只能猜：实测把 `Capital`/`Capitals` 单独拿出来会译成「首都」「大写字母」，
   有文档背景时才是财务语境正确的「资本」。

同一份 30 页教材章节（405 行待译）的实测对比：

| | 接口调用 | 用时 | 重试 | 译文质量 |
|---|---|---|---|---|
| 初版（校验规则误判） | 136 次 | 501 秒 | 6 次 | 有错译（`Capitals` 被逼成「首都」） |
| 修掉误判后 | 30 次 | 194 秒 | 0 | 正确 |
| **再加批量预翻译** | **9 次** | **54 秒** | **0** | 术语更专业（合伙企业 / 有限责任公司） |

### 关掉推理模型的「思考」（省钱大头）

2026 年的新模型很多是**推理模型**：回答前先输出一大段思考，而**思考 token 按输出计费**。
批量翻译这种任务不需要思考，不关掉就是纯烧钱。实测（DeepSeek-V4-Flash 翻同一页 51 条术语表）：

| 请求方式 | 耗时 | 输出 tokens | 能解析 |
|---|---|---|---|
| 默认（带思考） | 18.5s | 2340 | ✅ |
| `thinking: {"type": "disabled"}` | **3.1s** | **359** | ✅ |
| `enable_thinking: false` | 6.3s | 355 | ✅ |
| `chat_template_kwargs` | 7.4s | 364 | ❌ |

所以在预设代号里写一行就够：

```json
"ds4": {
  "baseUrl": "https://api.siliconflow.cn/v1",
  "apiKey": "sk-…",
  "chatModel": "deepseek-ai/DeepSeek-V4-Flash",
  "thinking": false          // ← 关键：docbridge 会翻译成 thinking:{"type":"disabled"}
}
```

不写这个字段就原样不发该参数（别的端点可能不认它）。
另外注意**别在 同类项目 里选这类代号**：它不认识 `thinking` 字段，
拿到带思考的推理模型反而更慢——所以文档翻译和语音翻译各用各的代号。

### 硅基流动上的 DeepSeek 选择（2026-09 实测）

| 模型 | 单页 51 条耗时 | 输出 tokens | 说明 |
|---|---|---|---|
| `Pro/deepseek-ai/DeepSeek-V3.2` | 48.8s | 399 | 付费保障档；术语质量好 |
| `deepseek-ai/DeepSeek-V3.2` | 16.6s | 398 | 同一模型的标准档，**快 3 倍** |
| `deepseek-ai/DeepSeek-V4-Flash` + 关思考 | **3.1s** | **359** | 首选：最快且 token 最少 |
| `deepseek-ai/DeepSeek-V4-Pro` | 61.1s | 2825 | 推理模型，思考吃掉大量输出 token，不适合批量 |

> 「Pro/」前缀是硅基流动的**付费保障档**，不是更强的模型——同一模型两个档位质量一样，
> 标准档还快得多。目录里目前还没有 V4.1（2026-09-11 刚发布，尚未全量）。

## 页面上有什么

* **拖拽上传**（.pdf / .docx，默认上限 200MB），自动识别格式并只列出可用模式；
* **模式与参数**：参数控件由管线声明的 `OPTIONS` 自动生成，加参数不用改前端；
* **预设代号选择 + 「测试通道」**：真发一次最小请求，立刻知道这个代号能不能用；
* **实时进度**：SSE 推送进度条、当前阶段、以及管线日志（含 `[warn]` 高亮）；
* **结果页**：下载译文 / 下载原件、统计卡片（单元数、页数、跳过、字符、接口调用、未译处）；
* **在线预览**：PDF 译文与原件并排翻页对照（服务端渲染 PNG，不下载也能看效果）；
* **最近任务**：只显示你自己 IP 提交的任务，过期自动清理；
* **管理页** `/admin`（`ADMIN_TOKEN`）：当日用量、估算成本、任务列表、管线健康度。

## 关键设计（为什么这么做）

* **绝不静默错位**。管线要求 `translate()` 返回**严格等长同序**；长度不符立刻抛错、
  整个任务失败，而不是把译文错位贴到别的段落上。翻译层内部会做校验
  （数量/换行、合并、繁体、省略号、元注释），不过就带着**针对该原因的**纠正提示重试，
  仍失败则按 20→5→1 的粒度分组重试（不是一上来就逐条，否则一个 51 条的批量失败会变成
  51 次请求），单条彻底失败时**保留原文**并计入「未译处」——宁可留一句英文，也不丢内容。
* **「合并检测」只看相邻行**（这条很反直觉，别改回去）。术语表里 `Capital` 与 `Capitals`
  本来就都该译「资本」、`Easy` 与 `Ease` 都该译「容易」；早期版本把「任意两条不同原文撞译文」
  判为模型合并，结果把**正确的**译文拒了：白重试 3 次 → 退化成 51 次单条请求，
  更糟的是纠正提示里的 "repeated" 会逼模型把正确的译文改成不同的词
  （线上实测：`Capitals` 从正确的「资本」被改成了错译「首都」）。
  现在只在**相邻**两条原文都够长且译文完全相同时才判为合并。
* **密钥只在服务端**。浏览器只拿得到代号与名称；`/api/config` 有测试专门断言不出现任何密钥字段。
* **任务目录隔离**。每个任务用自己的上传目录、输出目录与翻译缓存目录
  （既有 PDF 流水线的缓存键是「文件名」，同名文件会串缓存，任务目录天然隔开）。
* **原子落盘**。所有管线先写 `xxx.part`，成功后再 `os.replace()`；失败绝不留下半成品顶掉同名文件。
* **图片零改动校验**。PDF 原位管线会解析上游自检行并用 PyMuPDF 独立复核图片数量，
  不一致就判定结果不可信并抛错——这是「图不动」这个承诺的兜底。
* **数学符号不会被丢掉**（教材/论文刚需）。三层保障：
  ① 提示词强制保留 `√ ∑ ∫ ∂ ∆ ≈ ≤ ≥ ± ∞` 这类符号（写成中文「根号/求和/积分」也算对）；
  ② 校验兜底——译文丢了源文里的符号就带着针对性提示重试（**不误判**：`√2` 译成「根号2」是正确译法）；
  ③ 字体兜底——中文主字体（uming 明体）缺 `∂ ∆ ⊂` 这几个字形，缺字自动改用 DejaVu Sans 回退字体绘制
  （实测 20 个常见数学符号：uming 17/20、DejaVu 20/20）。缺了这一步，符号会静默画成空白。
* **多用户**：默认 3 个 worker 并行；排队按来源轮转（一个人连传 10 个文件也不会把队列占满）；
  可选每来源的并发/每日额度（见配置表）。
* **服务重启可恢复**。任务元信息落在 `_jobs/<id>/meta.json`，启动时恢复，
  重启后已完成的译文仍能下载；被中断的任务标记为失败（产物不完整不可信）。

## 配置项（环境变量，全部可选）

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` / `HOST` | `8788` / `127.0.0.1` | 监听地址；正式部署只监听本机，由 Caddy 反代 |
| `PROFILES_FILE` | `docbridge/profiles.json` | 本站的模型/密钥配置（与语音站分开两条线） |
| `ADMIN_TOKEN` | 空 | 管理接口令牌；不设则管理接口整体关闭 |
| `DOCBRIDGE_MAX_UPLOAD_MB` | `200` | 单文件上限 |
| `DOCBRIDGE_WORKERS` | `1` | 并行任务数。PDF 原位管线内部有全局字体状态，`1` 最稳 |
| `DOCBRIDGE_JOB_TTL_HOURS` | `6` | 产物保留时长，之后连目录一起清理 |
| `DOCBRIDGE_TRUST_PROXY` | 关 | 反代后面设为 `1`，否则用量统计里所有请求都是 `127.0.0.1` |
| `DOCBRIDGE_URL_PREFIX` | 空 | 用 Caddy `handle`（不剥前缀）挂载时设 `/doc` |
| `DOCBRIDGE_LIVE_URL` | 空 | 页头「同声传译」链接地址，留空则不显示 |
| `DOCBRIDGE_JOBS_DIR` / `DOCBRIDGE_USAGE_FILE` | 项目内 | 任务与用量文件位置 |
| `DOCBRIDGE_WORKERS` | `3` | 同时执行的任务数。PDF 原位任务内部有锁会串行，真正并行的是 Word / OCR 任务 |
| `DOCBRIDGE_MAX_ACTIVE_PER_IP` | `2` | 同一来源同时排队/执行的任务上限 |
| `DOCBRIDGE_MAX_JOBS_PER_IP_PER_DAY` | `0` | 同一来源每天的任务上限（`0`=不限；公开站点建议设 20~50） |
| `DOCBRIDGE_PREFETCH_WORKERS` | `3` | 批量预翻译的并发批次数。**决定 700 页要跑多久**：实测 405 行（9 批）3/6/9 并发分别为 45.9 / 32.3 / 20.7 秒，线上取 4 |
| `TRANSLATE_CONCURRENCY` | `3` | 单次批量翻译内部的并发请求数（预翻译开启时基本用不到） |
| `TRANSLATE_CHUNK_LINES` / `_CHARS` | `60` / `6000` | 每批送多少条/多少字符 |
| `TR_PRICE_IN` / `TR_PRICE_OUT` | `1.0` / `2.0` | 成本估算单价（元/百万 token），按你的模型改 |

## 测试

三个测试文件都是**离线**的（用假翻译函数，不联网、不花钱），样例文件现场生成：

```bash
cd docbridge
python3 tests/test_translator.py       # 翻译层：批量/校验/重试/兜底/配置
python3 tests/test_pdf_inplace.py      # PDF 原位：图片数量与像素一致、原子落盘、并发不串线
python3 tests/test_pdf_bilingual.py    # PDF 双语：页数 1:1、版式、译文确实画上去
python3 tests/test_docx_pipeline.py    # Word：两种模式、表格/页眉、样式保留
python3 tests/test_app.py              # 站点接线：提交校验、SSE、下载、用量、取消、磁盘恢复
```

（写成标准 `test_*` 函数，装了 pytest 直接 `python3 -m pytest tests -q` 也能收集。
请**顺序执行**：`test_pdf_inplace.py` 跑完会清理 `tests/_tmp/`，并发跑会互相清目录。）

另外有一个环境自查工具（部署后建议跑一次）：

```bash
python3 tools/check_pdf_font.py
```

它会回答三个问题：流水线**实际**用的是哪个中文字体、译文是否真的画上去了、
译文能否被复制出来。第 3 点最容易被忽略——见下面「已知限制」里的字体那条。

## 已知限制（都是真实存在的，别到时候惊讶）

* **取消是合作式的，不是秒停**。点「取消」后任务会在**下一个页/批边界**停下——
  正在飞的那个翻译请求不会被掐断（HTTP 请求无法中断），所以大文件可能要等十几秒到一两分钟。
  排队中（还没开始）的任务则立即取消。
* **PDF 原位的原文仍在文件里**。既有 `pdf_translate.py` 的做法是用底色矩形**盖住**英文再原位重绘中文，
  所以复制/搜索译文页时拿到的是英文原文——这是上游生产代码的既有行为，包装层没有改变它。
  视觉上完全正常，介意「文本层」的话请用双语模式。
* **输出体积**：两种 PDF 模式都会做字体子集化，所以成品通常只有几百 KB
  （实测 2 页样例：原位 289KB、双语 313KB）。子集化失败时会退回整份嵌入，
  文件可能大到十几 MB——`detail` 里会写明「字体子集化 9.8MB -> 289.3KB」，
  看到「字体子集化未执行」就说明字体选得不对（见上面字体那条）。
* **双语模式下 90°/270° 旋转页**：`show_pdf_page` 不跟随源页的 `/Rotate`，
  这类页的原文半页会与阅读器显示方向差 90°（内容完整不裁切，计入 `rotated_pages` 并在结果说明里提示）。
  0°/180° 正常。
* **中文字体要配对，否则译文「看得见却复制不出来」**。Linux 上若没装 CJK 字体，
  PyMuPDF 会退回内置 `china-s`：字形正常显示，但 PDF 里缺 ToUnicode 映射，
  复制/搜索译文会得到乱码（双语模式下实测 280 个乱码控制字符）。
* **字体还要挑 TrueType 轮廓的，否则输出会被撑大几十倍**。Noto CJK 是 CFF/OTF 轮廓，
  PyMuPDF 的字体子集化对它无效，整份 ~20MB 字体会被嵌进每一份输出。
  同一份 2 页样例实测：
  Noto Serif CJK → **19.6MB**，明体 uming → **61KB**，文泉驿 wqy-zenhei → **25KB**。
  所以候选清单（`pipelines/fonts.py`）把 TrueType 字体排在前面。
  解决：`apt install fonts-arphic-uming fonts-wqy-zenhei`，或让 app.py 自动探测。
  用 `tools/check_pdf_font.py` 可一键自查。
* **扫描版 PDF 不支持**（文字本身是图片），需要先 OCR，属于另一条流程。
* **竖排文字跳过**、保留原文；已是中文/纯数字的行不送翻译（计入「跳过」）。
* **Word 的这几类内容不翻译**：内容控件 `w:sdt` 内的段落、文本框内文字、
  SmartArt/公式内文字；含域代码（目录、页码、交叉引用）或超链接的段落**整段跳过**以免破坏版面
  ——所以目录、页码这类内容会保持原文。
* **老 `.doc`（97-2003）不支持**，请先另存为 `.docx`。
* **在线预览只支持 PDF**；Word 请下载后用 WPS/Pages/Word 打开。
* **没有登录系统**。任务 id 是随机 12 位十六进制、不可枚举，拿到链接的人就能下载结果；
  若要严格隔离，应在 Caddy 上加 Basic Auth 或接入你自己的鉴权。
* **PDF 原位管线在进程内串行**（内部要临时替换上游模块的全局函数以保证线程安全），
  所以多个 PDF 任务是一个接一个跑；Word 任务可并行。
